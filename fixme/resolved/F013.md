## This is the promoted rule's own predicted next face

`board/README.md` promoted the three-verdict rule on 2026-09-01 from
three kaizens of 2026-08-28, and its closing sentence is:

> The mechanism, where it exists, is the third verdict printed as its own
> line: `tools/launch.sh:302` prints `· … not checked from here` instead
> of a ✗ … **Two call sites; every other `--check` in the tree still has
> two verdicts, which is where the next face will come from.**

The next face came from the same file, eleven lines above the mechanism,
about six hours after the rule was marked and approved.  The rule
predicted where and the prediction held — which is the strongest thing
that can be said for a promoted lesson, and it is worth more than the
defect costs.

It is also the *same original incident* repeating.  The 08-28 case was
`launch.sh check` saying ✗ on a state directory that is read-only to a
session by design, because the check "was written to read the grant as
`run` reads it" and inherited `run`'s seat.  Line 302 was fixed.  **Line
287 reads the grant the same way and was not**, because the fix was made
where the symptom appeared instead of where the cause lived.

## Why it matters more than a cosmetic wrong word

The check does not stop at the two ✗.  It carries them forward:

    ✗ keep refuses this grant here — llm would not run: keep: nothing to
      grant at '/sys' — it does not exist.
    NOT installed — the lines marked ✗ say what.

So a session that runs `launch.sh llm check` to find out whether it can
run a led turn is told the node is unrunnable and the install is broken.
Both are false.  This tree's whole answer to "can I do X here" is to run
the checker, and from inside the fence the checker currently says no to a
node that works.

## The fix's shape, which the file already contains

Line 302's pattern, applied at 287: when the path is missing **and**
`TEND_FENCED=1`, print the third verdict — *not visible from this seat;
the fence does not bind it, and the runner runs from the person's side* —
rather than ✗.  Unfenced, a missing path is still a ✗ and should be.

Two things to get right, named because the obvious version gets them
wrong:

- **Not every missing path under the fence is the fence's doing.**  A
  grant naming a genuinely absent directory is a real defect, and a
  fenced check cannot tell the two apart — which is exactly what the
  third verdict is *for*.  It must say "I cannot see this", never "this
  is fine".
- **The rolled-up lines have to agree.**  If 287 stops being a ✗ then the
  `keep refuses this grant here` line and `NOT installed` must stop
  counting it, or the summary keeps asserting what the detail withdrew —
  which is `F011` and `F012`'s shape a fourth time: a roll-up that means
  something other than the lines it rolls up.

## Fixed — 2026-09-01, and it was three call sites, not one

A `cant()` helper beside `ok()` and `bad()`, printing `·` and setting
`unseen=1`, at every place the fenced seat cannot distinguish *absent
here* from *absent on the machine*:

- **the grant's paths** (`:287`), the entry's original finding;
- **`keep` itself** — with unseen paths in the grant, the question is not
  put at all, because keep refusing a path the fence hides is the fence
  answering.  This produced the loudest false sentence of the four:
  *"keep refuses this grant here — llm would not run"*;
- **the loader** (`:269`) — **a third face found while fixing the first
  two.**  With the two paths repaired, the check still said `NOT
  installed`, and the remaining ✗ was `llama-server cannot load — not
  found by the loader: libdnnl.so.3 …`.  Those libraries live under
  `/opt/intel/oneapi`, which the line *directly below it* already said
  the fence does not bind.  One symptom had been fixed twice while its
  third face sat two lines away — the same mistake as the 08-28 repair
  that fixed line 302 and left 287.

`unseen` is set only where the answer could have changed the verdict.  An
absent `allow-try`, a state directory read-only by design, a `make` the
runner performs — all still print `·` and none of them buys the third
verdict, because they are checked and known fine rather than unknown.
That guard has its own test: **a fenced check with nothing hidden still
says `installed`**, or the third verdict would swallow the other two
exactly where this command is read most.

## The roll-up, and the exit code

`NOT installed` now requires a ✗.  With no ✗ and at least one unseen, the
summary is *"not said from this seat — nothing here is red, and nothing
here is a verdict"*, which is the only true sentence available.

**And three verdicts got three exit codes**, which was nearly missed.
The first fix left `exit $fail`, so the real `llm` check went from exit 1
to exit **0** — and `test/test_launch.py:133` gates two live-node tests
on `returncode == 0`.  Those tests would have started running inside the
fence, against a node that cannot start here.  The comment beside that
line, written 2026-08-28, says why in advance: *"a guard that asked less
than the check ran the node on a machine that could not."*  A seat that
cannot see **is** a guard that asked less.  So `check` exits 0 installed,
1 not installed, **2 no verdict**, and the two tests still skip.

Measured after: `tools/launch.sh llm check` from inside the fence exits 2
and prints four `·` and no ✗; `test_launch.py` is 47 passed, 2 skipped.

## What would make this entry wrong

If `launch.sh check` is only ever meant to be run from the person's
shell.  Against that: `tools/fence.sh` prints the in-force line at every
prompt precisely so a fenced session knows where it stands, and this
session reached for the checker for exactly that reason without being
told to.  A checker that is only valid from one seat should say so in its
own output, which is the same fix.
