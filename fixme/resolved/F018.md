## What was measured, 2026-09-03

**The mechanism.**  `tools/keep.py` builds a Landlock ruleset over
`SYSTEM_READ` (`/usr /etc /lib /lib64 /bin /sbin /proc /dev`) and the
grant's `allow`, `allow-try`, `write` paths, restricts itself, and
`execvp`s the program line's first word.  A home directory is under
none of those, so `~/.local/bin/llama-server` is unreadable to the
runner — and `execvp` treats EACCES on one PATH entry as "keep
looking", reporting it only if nothing else is found.  With
`/usr/local/bin/llama-server` further down PATH, something else is
found: the bare SYCL binary, without the fourteen oneAPI directories
`setvars.sh` puts on `LD_LIBRARY_PATH`, which is the 15:25 death again.
So the symptom is exactly "hyppää sen yli": not an error, a skip.

**Why the check missed it.**  Line 319 of the previous `launch.sh`:
`found=$(command -v "$prog")` — the shell's resolution, with the
shell's PATH and the shell's reach.  The check already knew that its
seat is not the runner's for libraries (the 08-28 ldd line compares
every shared library's real path against `SYSTEM_READ` and the grant),
but never applied the same rule to the program itself; and a script,
having no dynamic section, gets no ldd line at all.  Two faces on
node-install day, and this is the third of the same defect: the check
answering from where it sits.

**The fix.**  The read set (`SYSTEM_READ`, the grant's paths, `$STATE`)
is computed once, before the program is resolved, and a function
`keep_reads PATH` says whether a real path is under it.  For a bare
program word the check walks PATH itself, twice in one loop: the first
executable entry is what the shell would run, the first executable
entry keep can read is what keep would run.  Equal: ✓ as before.
Different and keep's exists: *✗ program X → A for you, and keep would
skip it — outside what keep lets it read — and run B instead (F018)*.
Keep's missing: *✗ … keep would find nothing … no other X on PATH*.
An absolute program keep cannot read: *✗ program P is there, and keep
would refuse it*.  The ldd line still runs on the binary keep would
actually run, so a second defect under the first is still reported.
`command -v` naming a builtin (`true`, in the port test) is resolved to
the first PATH entry, since keep's execvp knows no builtins — found by
the suite, not by a reader.
