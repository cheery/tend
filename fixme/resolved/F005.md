    suspected  measured: `pull` starts the runner detached and then polls every 50 ms, up to 600 times, for the lock to be *held* before it says "started" (`tools/launch.sh`, the pull case).  A runner that dies at the loader takes the lock and drops it inside one poll, so the poll never sees it held and runs its full 600 — thirty seconds, the test's exact timeout.  The same suite passed for the commit before, so the race had been landing on the right side of a 50 ms window until this afternoon
    gate       test/test_launch.py::test_a_runner_that_dies_writes_one_line_to_the_andon_record — the test that caught it; its 30 s timeout is the bound the wait must stay under, and the death notice it reads is written before the wait can end
    see        card:canvas.md (the death notice, day two), tools/launch.sh, test/test_launch.py

The wait's purpose is to say "started" truthfully — not before the
runner holds the lock.  A runner that has already come and gone is
the other way the wait is done, and it leaves one trace the pull can
read: `stopped`, newer than the pull line the same command just
appended.  The wait now ends on either — the lock held, or `stopped`
newer than the pull file — and the poll cap stays as the bound.  Dash's
`-nt` compares below the second (measured on this machine: two files
0.2 s apart), which the same-second stamps above require.

What this is not: the pull saying "started" for a runner that died a
second later was Henri's original complaint (2026-08-28 13:27), and the
death notice was that fix — the runner's own stop writes the line, and
`pull` stopped watching for it.  This entry is only the wait that was
left behind the notice, counting to thirty for a lock nobody held.
