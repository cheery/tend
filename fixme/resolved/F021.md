## Why it was not a fix on the first sighting

The 08:50 kaizen read it right: a board gate that tracks an approved rule
by line number mis-fires when a large edit above it shifts the rule, and
the working tree's move is invisible to `git log -L` until it is
committed.  One sighting was the diligence — `rule_dirty` False, the
rule's real last change 2026-08-28, before the approval — and a skip by
the person's hand.  The second sighting, the same day, is the ledger's
rule for the shape: a defect that costs the person a `--no-verify` each
time a session tidies the board is a mechanism owed, not a note.

## The fix, and what it does not do

`git diff HEAD -U0` is the same reading `rule_dirty` makes.  Every hunk
whose new-side range ends above `a` moves the rule by its added-minus-
removed count; a hunk that crosses a..b is dirt and was refused a line
earlier; a hunk below moves nothing.  So a..b minus the shift is the
rule's own lines in HEAD, and `-L` follows them through history as it
always did.  It does not cover an edit *inside* the rule (that is
`rule_dirty`'s, and it stays red), and it does not read the index —
the hook's tree is the working tree, which is the seam F008's fix chose.
