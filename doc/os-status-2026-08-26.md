# spec/os.md — a status pass, 2026-08-26

*A session's reading, at Henri's "check which ones are already

## Satisfied — built and evidenced

* **13, programs start by pull; no pull → self-shutdown.**  The resolver
  (`tools/resolve.sh`), the launcher (`tools/launch.sh`), idle-stop —
  shown end to end today for two programs (the node and `llama-server`).
* **14, errors are not silent.**  Rule 9, everywhere: keep refuses
  rather than run unconfined, the leash logs `plain` vs `scope`, the
  fence-hook refuses with a reason, the lamp, the kaizen.
* **9, may crash but not hang.**  `tools/leash.sh` treats a hang as a
  crash (exit 124); the launcher stops on idle.  *(The crash-loop
  backoff + andon half is owed — `board/cords.md`, blocked.)*
* **8, open where left; interaction must not break each other.**  The
  state file is where a node is left; keep isolates each program's
  state read-only from the others, and the one-runner-per-state lock and
  the two-writers-apart (pull vs run) keep them from colliding.
* **11, hard to attack from outside.**  The fence — bwrap namespaces, no
  network by default, empty home, read-only `/usr`, unshare-all.  For a
  no-network fenced process the external surface is near nil.
* **7, runs Linux without weakening security.**  Decided (`vision.md`);
  the fence/keep/leash are the security, over Linux.
* **Open problem 1 — how are users' data protected from programs? —
  CLOSED today.**  This was `keep`'s `because`; the grant beside the
  program answers it: a program reads/writes/reaches only what it was
  handed.  One of the three real problems on his sheet, answered.

## A simple solution is already here (present mechanism, small work to claim fully)

* **1, auditable and bounded from its own interface/spec.**  The grant
  file beside each program *is* the interface it is bounded from; the
  leash ledger and the plain state file are the audit.  Substantially
  here as of today.
* **5, install-config recorded in the node; reconfigurable by pull.**
  The grant file + the state directory are the config recorded in the
  node.  *(The "from wherever it came" provenance half needs the store —
  see open problem 2.)*
* **2, testing a program's installation should not be hard.**
  `tools/toolbox.sh` (says what's missing) + `node/grant` + the stranger
  test give a node a run-it-and-pull-it install test.  The simple
  extension is a declared toolbox *manifest* — the surviving half of the
  withdrawn toolbox idea.
* **3, designed secure.**  Not a feature but the tree's stance, in force
  and evidenced (fence, keep, protected set, restraint-outside-write).
* **4a, every part testable.**  The suite + gates + the mutation harness
  (`board/green.md`) enforce it.
* **6a, no central server by default.**  Plain files, no service, no
  account (`vision.md` "What tend won't be").
* **12, designed for AI use without threatening security.**  Today's
  frame — a session/model as a governed program — is exactly this; the
  one gap is the ambient-exec residual.

## In the air — no mechanism yet

* **4b, behaviour verified by types and automatic model checkers.**
  Nothing; Rust / the future-language territory.
* **6b, version marked / content-addressed identity.**  Needs the
  content-addressed store (named in `board/work-environment-ai.md`, not
  built).
* **10, localisation by the compiler.**  Nothing (future language).
* **15, the system produces its own programming language** (the 2015
  paper).  Nothing; bootstrap is Python + Rust.
* **16, encrypted disk as standard.**  Nothing — and partly reframed:
  `keep`'s boundary is *authority*, not secrecy, because `vision.md`
  wants the person to read their own data as plain files.
* **Open problem 2 (install half) — programs protected AND installed.**
  Protection is here (keep, the grant, state isolation); *installation*
  — a content-addressed, signed store, pull = fetch-by-hash — is in the
  air.
* **Open problem 3 — stay fast when closed the moment they're not
  needed.**  The pull lifecycle closes them; *fast restart* is restore
  latency.  Light programs restore instantly (the node's state file);
  heavy ones do not — `llama-server`'s ~30 s cold load is this exact
  problem, live and unsolved (CRIU/serialize-restore is "in the pocket",
  not built).

## The shape of it

The **program** properties are mostly satisfied or nearly so — pull,
bound, isolated, non-silent, crash-not-hang, data-protected.  What is
**in the air** clusters in two places: the **language/verification**
future (4b, 10, 15 — Rust-and-beyond, not this phase) and the
**store + restore-latency** layer (6b, open problems 2 and 3 — how a
program is identified, fetched, and made fast again).  The security
stance (3, 11, 12) is in force; its one live gap is the ambient-exec
residual, which is the session-as-principal work, not a program gap.

Most striking: **open problem 1 is closed as of today**, and property 2
(install testing) — where Henri's toolbox idea was aimed — turns out to
be the simple-solution-nearly-here, served by a manifest rather than by
enforcement.
