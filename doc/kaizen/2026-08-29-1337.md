## What went right, and why

**Red first held all day, and it paid.**  Every pass ran its new tests
against the previous commit's launcher and panel before the change;
five failed at the first pass, and each later pass's fixture found a
hole the earlier pass had not: `serve` silent on a node held before it
ever ran (no state directory, a lock that could not be opened read as
"a runner is up"); `check` clobbering `$root` in its own loop; a
mutate row breaking nothing since the `serve` rewrite.  Each was found
by a test that built the side it meant — a hold-to-death flow with a
scratch tree, a scratch node named by content, a hold older and newer
than a fixture death by explicit `utime`, two seconds apart.  The rule
`board/README.md` carries from 2026-08-26 was the instrument; nothing
here was found by reading.

**Henri's review was the design.**  "Name what I'm holding inside the
file" turned a filename-keyed hold into a pin-shaped one; "show holds
on the panel" made a held node a row whether pinned or not; "make sure
the error becomes visible" turned `held  not running` — a calm row
that was the hold's promise not kept — into a bold `HELD, NOT
RUNNING` that says which way; "the panel should have a tool" put the
person's hand where the person looks.  And "think critically and don't
just obey" on the state line found that the second pass had accepted
`state` in a hold without anything honouring it — the resolver runs
`NODE/state` only — so the honest build was a row that says *not
honoured yet*, not a feature.  Four passes in one sitting is not a
plan that slipped; it is a card whose day one was measured on the desk
between passes ("I ran the install, the node row looks right now").

**The gate caught the day's own lesson.**  `1f5ceb1` was refused once:
`test_resolve.py` inherited the environment, read Henri's live
`node.hold`, and started the real node into scratch — the fixture rule
in one more face, the same afternoon the launch helper had been given

(every test gets a canvas of its own, as it gets its own git identity),
not a patch per test.

## What went wrong, and whose

**The session's, twice at the commit line.**  The first refusal of
`4ae07e3` was `set -u` on an unset `HOME` under the fence — a path
expression written without thinking about the fence's environment; the
gate found it in `deliver.sh`'s fenced test, not the session.  Worse:
on the rename commit the session filtered the gate's output to
nothing, could not see why the commit was refused, and probed with
`git commit -m "x"` — which passed and landed a commit named "x", then
had to be amended.  A probe at the commit line is a commit.  The
instrument was `--dry-run`, or reading the output unfiltered.

**The session's: a hold keyed on the wrong thing.**  Day one took
"`<name>.hold` beside the pin" as the pin's *name* and not the pin's
*shape*, and Henri had to ask for the content to name the node.  The
card's own text said "node+state is being pulled"; the session built
the filename.  Reading the card's `because` against the build before
declaring day one would have caught it.

**The session's: a field accepted without a mechanism.**  The second
pass took `state` in a hold because the pin has one, and nothing on the
resolver's side ran any state but the default.  A field that nothing
reads is a promise on the person's side with no keeper; the fourth pass
had to make the panel confess it.  The rule: a line in a file the
person writes is a grant, and a grant without a mechanism that honours
it is a false row until one exists.

**The tree's, small:** `mutate.sh` prints `fatal: failed to write
commit object` from its scratch copy on every row; the rows still read,
so it blocked nothing, but a fatal that means nothing is noise that
will one day hide one that does.  Not chased today; named.

## What should change tomorrow

1. **A probe at the commit line is `--dry-run`**, and the gate's output
   is read whole when a commit is refused — never grepped to a tail.
2. **A field in a person-side file gets its mechanism in the same
   commit, or its row says "not honoured".**  `state` in a hold is the
   specimen; the instance per (node, state) is named on
   `card:hold.md` as the want it waits on.
3. **Read the card's `because` against the build before "day one
   landed."**  The filename-keyed hold would not have survived that
   reading.
4. **The resolver on a timer or at login is the next want on
   `card:hold.md`** — with nobody at the desk a held node that stops
   stays stopped until the next hook, and Henri asked "how do I run the
   resolver on the canvas" before he asked for the hand.  It is the
   first thing in this tree that would run when he is not there, so it
   is a rule-5 conversation before it is a build.
5. `mutate.sh`'s scratch-copy `fatal:` gets a look on a day with room.
