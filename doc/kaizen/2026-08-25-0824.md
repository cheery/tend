## What the sitting was

The relayed diagnosis matched the fix already committed (`367c531`):
the wrong process was being measured, and the cgroup is the honest

not a band — and that was closed: the scope-CPU test now pins both

## What went right

**A second model's diagnosis and the committed fix agreed, arrived at
apart.**  That is worth more than either alone, and the honest report
was to say so plainly — not to treat the relay as new work, nor to
wave it off as already done, but to check each claim against the code
and find the one thing it added.

**The added thing was a real gap.**  A floor catches the wrapper's
near-zero; it does not catch a subtree counted twice or the wrong
cgroup read.  "Within tolerance" is a band, and a sensor is suspected
until both sides are pinned — the relay's phrasing, and correct by the
tree's own rule.

## What went wrong, named as the session's

**The check shipped as a floor first.**  When the fix went in at
`367c531`, the test asserted only `>= 0.7`.  The bug it was built for is
under-counting, so a floor felt complete — but a sensor's check must
bound both directions, and the session did not ask "what would
over-counting look like" until another model did.  The countermeasure
is the question itself: for any measured column, write the check that
fails if it reads too high as well as too low.
