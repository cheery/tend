## What went wrong — named as whose

**The session's, and it cost Henri a prompt: `755 - 222` in decimal.**
The user-prefix branch of `install.sh` spelled its mode by arithmetic
on an octal literal — 533/422, `-r---w--w-` — and the same script did
not recognise root as root, so `sudo tools/install.sh` took that branch.
Two mistakes in one line, and the test that "held" the mode asserted
only *not writable by owner*, which 533 satisfies.  The lesson is the
manifesto's: the test measured the wrong property.  The replay is in
the suite now as `0o022/0o033`, the modes spelled out, root recognised.

**The session's: it ran unfenced for the fix.**  With the hooks off,
`TEND_FENCED` was unset for this session's commands.  It confined
itself to `install.sh`, its test and `git add`, and said so — but
nothing enforced that; it was the restrained party's word.  The right
order would have been: restore the fence first, then touch anything.
The session asked for the restore only after staging.

**Nobody's: `--check` fell over on `sed` instead of saying "unreadable."**

**The session's, found by the gate at 16:40: the prefix could not

1. **A test that guards a mode asserts the mode**, not one bit of it.
   Applied here; worth a grep across the suite for other `os.access`

2. **When the fence is found down, the first line is the restore**, not
   the fix — `tools/fence.sh --force` (or `--restore`) before any edit,
   and the session says it is unfenced in its first sentence, not its
   last.
3. **Day two of `install` is now real work**: the tree's copies are
