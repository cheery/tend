# Kaizen, 2026-08-25 07:53 — the leash's first outside user found a defect in the leash

*Written because the lamp lit on the cpu-column fix.  A gestate session
ran tend's leash on its full suite, read the ledger, and relayed
through Henri that `cpu=1.3s` could not be right for a twenty-five-
minute CPU-bound run.  It was not.*

## What the sitting was

One defect, read from the code and fixed: `times` measures the shell's
own waited-for children, and in scope mode the work is a child of the
user manager, so the column read the `systemd-run` client and not the
suite.  Scope mode now reads the cgroup's `CPUUsageNSec`; plain mode
keeps `times`, which is right there.  A test guards it, and the card
carries the fix and what it still owes.

## What went right

**The ledger did its one job on its first outside run.**  The session's
own words: it would have had no way to notice without the line.  An
observer that catches a defect in the thing it observes, on day one, is
the case for the observer existing at all — which is exactly what
`doc/mediation-order.md` said the ledger was for.

**The fix cannot lie, even unverified.**  Scope mode now yields the
cgroup number or an honest `?`; it can no longer report the 1.3s that
started this.  So committing it before the demonstration cannot regress
the ledger below honest — the pattern `gates` and `fence` used, not a
blind change.

**The reporter's diagnosis was tested against the code, not trusted.**
It guessed "counting the wrapper, or read after the scope is gone."
Reading the code confirmed the first and turned the second into the
fix's own risk — the read is placed before the stop, and the race it
named is the thing the demonstration must still rule out.

## What went wrong, named as the session's

**The demonstration cannot be taken from where the session sits, and
that is the fence working as designed against the session's
convenience.**  Every run here is plain, because the bus is off; the
scope path is unexercised.  The session wrote a fix it cannot run.  The
honest form is the commit body saying so — parsing verified, cgroup
read not — but a reader should weigh that the load-bearing line has not
executed once.

**The `?` fallback trades one risk for another.**  If `CPUUsageNSec`
races the scope's teardown to empty on the gestate machine, the ledger
will read `cpu=?s` and the number is lost, not wrong.  Honest, but the
whole point was to have the number.  If the demonstration shows the
race is real, the fix is a transient service with `--wait` rather than
a scope, and that is the next iteration, not this one.
