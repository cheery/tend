# Kaizen, 2026-08-26 15:09 — a 1-in-10 counted, two causes read off the ledger, and a script that died before it wrote

*Written because the lamp lit on Henri's commit of the hook line, and
on the commit after.  Henri: the ten-line loop — "1 failed, 7
deselected in 10.92s", then nine passes.*

## What the sitting was

The flake counted: 1 in 10, the first run, 10.92 s.  The leash ledger
— visible from a fenced seat because the state row passes it through —
had the signature: eleven runner records for ten tests, one `exit 75`
with 0 s wall that *started* ten seconds after its test did.  Two
causes, both measured: the resolver tested the lock by taking it, and
a runner that tried in that moment was turned away; and the leash's
scope path started a runner ~10 s from cold on Henri's seat.  Fix in
`run.sh` (the runner waits 2 s for the lock) and `resolve.sh` (30 s
wait, honest message), a deterministic test for the race, all in
`resolver-lock.patch`; three cards updated.

## What went right

**The count came before the reasoning, and the ledger did the
reasoning.**  Ten runs gave a rate; the ledger gave the mechanism
without touching Henri's seat again — the 0 s `exit 75`, its start
time, and the epoch's meaning (`start=$(date +%s)`) settled in three
reads.  The green card's fourth shape got its name from a number, not
a mood: a detector whose subject differs by seat.

**The race got a deterministic test.**  Hold the lock 0.3 s, start the
runner, it must run: red against the old launcher, green with the
patch.  A 1-in-10 became a 1-in-1.

## What went wrong, named as the session's

**A script asserted before it wrote, twice, and I read the patch's
line count instead of its content.**  The pass that shortened the wait
to 2 s and lengthened the refusal test's runner to 4 s asserted on
`flock -w 5` first — which the "red against the old file" step had
just copied away — and died; the test edit never landed.  Three
failing verifications, two probes that passed by hand because my hand
typed 4.0, an instrumented run that died on the *same* missing text —
before `grep idle="1.5"` on the copy said what was there.  Cost: forty
minutes and four patch regenerations.  The countermeasure is the one
this tree already uses for verdicts: **a patch is read for what it
contains, not how long it is** — `grep` the hunk you meant to add
before verifying anything downstream of it.  And a scratch copy that
one step overwrites is a scratch copy the next step cannot trust;
"red against the old file" belongs in its own copy.

**The resolver's check was designed to take the lock it tested.**
`flock -n lock true` was the obvious idiom and it holds the lock for
the length of `true`.  The runner-side wait is the right fix; the
design was the session's, and it was wrong in a way the tests here
could not show because the collision needs a slow start to widen the
window.
