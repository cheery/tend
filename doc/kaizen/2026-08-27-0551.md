error.**  I had written "37 kaizens on 08-26" into four places from an
eyeball; `ls | grep -c` and gestate both said 39.  Corrected beside the
original in each place — the same "measure, don't assert" the batch-2
ingestion had just promoted, applied to my own number.

**The clone rule did not repeat the mistake it describes.**  Before
writing "use a clone," I cloned the tree and measured it: own `.git`,
`core.bare` untouched, protected files writable, suite green (11), a
`fetch` that works inside the fence.  A rule about not-declaring-the-

the commit that states it.

**The all-deleted tree was diagnosed, not panicked over.**  When main
suddenly reported every file deleted, the cause was one flipped bit
(`core.bare`), found by reading git's state rather than reacting to the
scary status.  Main was never actually damaged.

**The /feedback question was answered honestly against my own

**The reworded rule was demonstrated live.**  The lamp lit through the

## What went wrong, named as the session's

**The worktree.  This is the sitting's real fault, and it is large.**
I reached for `git worktree` to get a writable copy of a protected
script — and I already had a working method (a scratch copy; 13 tests
had passed against it).  I abandoned the method that worked for one
that broke the tree, and then, after the *first* `core.bare` flip, I
pushed the worktree further instead of stopping.  It flipped again, and
a backgrounded rebase leaked into the tree.  Two breakages, both after
the warning.  The countermeasure is now a rule and a memory
(`clone-not-worktree-in-the-fence`), but the deeper miss was not
heeding the first sign — the exact "reading a warning is not applying
it" strand batch 1 named, one more face.

**Backgrounding a git write.**  I sent `git commit && git rebase` to
the background; it was killed at its timeout (exit 124) and left a
half-write in the main tree, in a read-only-bound file I then could not
revert from inside the fence.  A git write is never a background task —
a killed one does not roll back.

**The 37 was an eyeball where a `grep -c` was one keystroke away.**
The tree's whole method is measure-not-assert, and the count went in
un-measured and propagated to four files before another session caught
it.  Cheap to fix, cheaper to have counted.

**A correction to an old kaizen file fooled the lamp.**  The `37→39`
commit (4b4b3b1) modified `doc/kaizen/2026-08-27-0538.md`, and
`tools/kaizen.sh` treats any commit touching a `<date>-<HHMM>.md` file
as "the last kaizen" — so it reset its baseline to a correction and now
under-counts the sitting's uncovered commits.  Found writing this
kaizen; a real defect in the lamp's own detection, not yet fixed.

## What should change tomorrow

1. **Clone, never worktree; never background a git write.**  Now a rule
   (`board/README.md`, 481e0ee) and a memory.  The first sign that a
   tool is fighting the fence is the signal to stop, not to push.
2. **The lamp's "last kaizen" should match an *added* kaizen file, not
   a modified one** — else every correction to an old kaizen resets the
   baseline and hides commits.  A `git log --diff-filter=A` on the
   pathspec, or its own small card.  Named here; not fixed blind at the
   end of a sitting.
3. **Batch vs sitting — the refinement Henri predicted.**  He asked for
   a kaizen to "conclude one batch of work" while staying at the desk
   an hour more, and wants to try *batching tasks*.  The rule I wrote
   says one per sitting; he is using one per batch.  The rule's own note
   ("we won't get it right at the start") is already paying out — the
   unit may be the batch a person marks, not the desk-sitting.  Left for
   his refinement, not resolved by the session that wrote the rule
   (`board/kaizen-ingestion.md`, the self-shaped strand).
4. **The kaizen-unit patch landed by Henri's hand (9fb2400).**  The
   protected-file landing question stays open: a pull from a clone, or
   an unfenced lander, so a tested change reaches a protected file
   without his hand — `card:session-program.md` / `card:self.md`.
