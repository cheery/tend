## What went right, and why

**One question at a time was the right instrument.**  The board had
two `doing` cards parked on decisions nobody but Henri could take —
how the resolver runs with nobody at the desk, and which model leads.
Asked one at a time with the choices laid out, each got a sentence back
that was also the design: *"do not make it depend on systemd, but use
systemd in implementation for ubuntu"* separated the mechanism (the
tick and its stamp) from the carrier (a user timer) before a line was
written; *"build capability for both gemma and claude, also I'm
thinking about subscribing to openrouter"* collapsed "which model" into
"one wire, several doors", because the loop already spoke the OpenAI
chat wire and that is OpenRouter's.  Neither build took a decision the
session could not have taken wrong.

**Red first, done properly the second time.**  The first "red check"
was not one: `git stash push -- tools/ doors/` failed on the untracked
`doors/` and the twelve tests ran green against the new code.  The
second stashed the tracked tools and moved the untracked files aside,
and twelve failed against `bd94760` in four minutes — the door tests
timing out at 60 s each because HEAD's `lead.sh` waited on a port.
The rule from 2026-08-26 held: a fixture is a claim, measured like one;
and a red check that reports green is a fixture too.

**A field with no mechanism was not accepted this time.**  Yesterday's
lesson (`state` in a hold, honoured by nothing for two passes) was
applied twice: a kept turn through a door is refused with the reason,
not accepted and silently unkept; and a hold with no tick is a bold
row, not a calm one.  The tick's stamp is written by a tick only,
because a visit with a hand on it proves nothing about the nights.

**The key never crossed to the wrong side.**  Under the person's home,
mode 600, refused if in the tree or readable by others, sent to curl on
stdin (`-K -`) and never on an argument line, asserted absent from the
account and the proposal.  The test for "inside the tree" names a path
under `doors/` that does not exist, so the check's order — tree before
existence — is what the test measures.

## What went wrong, and whose

**The session's: a wrong clock in its head.**  For most of the sitting
the session believed it was 19:40 when it was 19:18 — it read the
sitting's start (18:52) and then paced itself against a time it had
not looked at again.  It cost nothing tonight and would have cost a
build another night: a session that thinks it has twenty minutes
narrows scope on its own.  The instrument is `date`, or the lamp's own
"28m in, 62m left", read before pacing, not remembered.

**The session's: the first red check was green.**  Named above; the
cause was a stash pathspec on an untracked directory, and the session
read "12 passed" as a result before reading the stash's own error
line above it.  Read the whole output, in order — yesterday's rule 1,
one more face.

**The tree's: `test_a_program_that_is_busy_and_silent_is_not_idle`
failed once.**  In the session's own full run (477 passed, 1 failed)
the launcher stopped an 8 s busy loop for idleness within a 2 s window;
the gate's run a minute later passed it.  Under load the CPU-progress
read missed a busy child — the same shape the work laptop found on
2026-08-28, now as a flake.  Not chased; named as owed.

**Not measured, and said so on both cards:** the timer overnight on
this desk (his `tools/install.sh --tick` after the install, the
panel's line next morning), and a live turn through either door (the
keys are his to put there; the model names are the doors' vocabulary
and a wrong one is a 404 on the first turn).

## What should change tomorrow

1. **Read the clock before pacing** — `date` or the lamp's line, at
   every decision about scope, never a remembered start time plus a
   guess.
2. **A red check is read from its first line.**  A stash or a move
   that fails makes the run after it a run against the new code; the
   count means nothing until the setup's own output has been read.
3. **The tick's first night is the measurement**: `sudo
   tools/install.sh` then `tools/install.sh --tick`, a hold on the llm
   node, and the panel in the morning.  If the line says `TICK STALE`
   the carrier is the story; if it says `NO TICK` the stamp is.
4. **The door's first turn decides the model names** — `tools/lead.sh
   llm --door openrouter` with a key in place; a 404 is a wrong name in
   `doors/openrouter/door`, and the fix is one line, his.
5. **`test_launch.py`'s busy-and-silent test flakes under load** — on a
   day with room, the CPU-progress read is measured against a loaded
   box, and the launcher's idea of "burning a core" is checked for the
   child it actually reads.
